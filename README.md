## 四层读者

和宝玉那套一样，文件按**谁读**分层；0.2.5 多了一层「用户」，0.2.6 在它前面加了「品类」：

| 层 | 文件 | 读者 | 是否进最终产物 |
|---|---|---|---|
| 调度 | SKILL.md | agent | 否 |
| **品类基准** | **registers/category-prototypes.md** | **agent（S1）+ 用户（G0 首行「这是 C_」）** | 否 |
| 判断依据 | references/ + tokens/ | agent | 否 |
| 选项货架 | registers/ + patterns/ | agent **+ 用户（G0 组合卡）** | 否 |
| 方向记录 | design/00-direction.md | 用户 + agent | 否（但要随交付列出） |
| 交付 | pass-a.html、pass-b.html | 人 | **是** |

中间几层都不进交付物。它们的唯一作用是让交付物里的每个取值有出处。**G0 之前「选项货架」只有 agent 读得到，这正是「模型定死一个方向给用户」的结构原因。**

**这个按需加载的收益率不高，得诚实说**：2,437 / 3,114 = 78%，只省 22%。原因和宝玉相反——出图只需要"一个风格 + 一个版式"，而 UI 需要全维度覆盖，绝大多数 references 都是必读。但 0.2.6 有一个反直觉的改善：新增的品类表 455 行**没有让比例变差**，因为 S1 只精读其中一个品类（约 110 行），不像表面/排印表必须整表读完做比较。**品类层是收敛器，不是新维度**——它减少的是「该从哪开始」的搜索空间，不是阅读量。

真正的节省不在 references，在**货架层**（见下）。

## 为什么 9 品类 × 6 调性 × 5 骨架 × 6 排印 × 6 表面只需 15 个文件

朴素做法是给每个组合写一份完整方案：9 × 6 × 5 × 6 × 6 = **9,720 份文档**，每份约 60 行 = 约 583,200 行，且大量重复。

本做法把维度**分层**，不是全部平铺：

- **品类（`category-prototypes.md`）**：给底面 / 字体 / 按钮 / 曲率 / 线宽 / 版心 / 密度 / 图文比 / 栏目顺序的**默认家族**（9 类 × 2 子型 = 18 套）
- 表面材质（`surface-recipes.md`）：只管明暗系统、底面/卡面/墨色/线/纹理
- 排印系统（`type-recipes.md`）：只管字族 / 行距 / 字距 / 线的性格 / 曲率 / 密度
- 调性（其余 registers）：只管结构外露 / 离地高度 / 禁忌
- 骨架（patterns）：只管区块顺序、每块职责、塌陷点

关键：**品类不参与相乘，它先收敛**。用户说「美妆」时，9,720 个组合里已经有 6 × 5 × 6 × 6 = 1,080 个被品类默认家族排除，只剩品类内部的微调。所以文件数只从 13 增到 15（品类表 + 品类实测器脚本），不是从 13 乘到 100+。

| | 朴素 | 本做法 |
|---|---|---|
| 文件数 | 9,720 | 15 |
| 维护行数 | ~583,200 | 1,351（品类 455 + 表面 200 + 排印 166 + 调性 181 + 骨架 215 + tokens 134） |
| 单次读取 | ~60 行 | S1 精读 1 类约 110 行；G0 整表读 366 行；组合细节仍 64 行（1 调性 + 1 骨架） |
| 覆盖起点 | 1 份 = 1 组合 | 15 份 = 18 个品类默认家族 + 其内部变体 |

**0.2.4 加的是第三维（排印），0.2.5 加的是第四维（表面），两者都不是为了凑组合数。**

- 0.2.3 之前所有页面共用一副脸，因为「排印」这一维压根没有货架，模型只能用默认值填，再被一致性纪律锁死。用户要的「什么场合该有什么文字」，本质是要有第三维可选。
- 0.2.4 的每一稿都是暖白底，因为「表面」同样没有货架：`scale.md` 的全站暖色相纪律 + 账本模板示例值 `#FBFAF7` 直接给定，而两条 R2 实测参考其实都是深底。用户要的是「按具体项目换底纹，且动笔前给几套组合让我选」。

**正交 ≠ 随便搭**：组合成立要在 `00-direction.md` 写清「受众×场合 → 为什么这几个值一起成立」，并在账本里逐行落值。

## 六阶段 + G0 的因果关系

```
S1 七字段 ─→ S1.5 内容位次 ─→ G0 方向确认门 ─→ S2 主张+承诺+放弃 ─→ S3 六列账本 ─→ S4 两稿 ─→ S5 十问+矩阵
   约束         P0/P1/P2/P3        ≥3 套组合          方向                取值           实现        检验
    │             │              用户选/授权           │                  │              │           │
 推不出决策    排不出 P0        没确认=第八问不过    不可反驳          无依据引用      无地板      有空缺/空格
 = 没填        = 没有主次        ≠ 用户认可          = 空话             = 作废         = 不通过    = 打回
```

S1.5 排在 G0 **之前**，是为了让方向卡能回答"这个 P0 配这套材质长什么样"；否则用户只能凭顺眼挑颜色，那正是 0.2.5 的失败方式。

每一步的产物是下一步的**唯一合法输入**。这是为"出错能定位"设计的：页面不对，先看 S5 哪一问不过，那一问指向哪个阶段，那个阶段的产物必然有具体一行是错的。

对比"一把梭"生成：页面不对，只能整体重写，且说不清哪里不对。

三处是刻意加的，宝玉那套没有：

1. **"放弃"列**。出图不需要说代价（图是死的，不承担任务）；界面必须说，因为界面要被人用、要被比较、要在两种方案间选。
2. **数值刻度表**。宝玉靠形容词（"手绘、温暖、纸张质感"），UI 靠数值。形容词能描述风格，描述不了 13px 和 16px 的差别。
3. **状态矩阵**。这是前面调研的所有 design skill 的共同空白——它们产出的东西像设计稿，因为截图里只有主态。

0.2.5 又加了一处：**方向确认门**。宝玉那套是"输入一段内容 → 出一张图"，风格由 agent 内部选定；UI 会被人长期使用、承载品牌身份，方向不能由模型单方面定死。

## 与宝玉那套共享的两条纪律

- **中间产物落盘**。不是为了存档，是为了让下一步有东西可读、出错能定位。
- **禁止事后修补**。宝玉禁"后期贴字改错字"，这里禁"事后美化"（加阴影改颜色提升质感）。理由相同：无依据的局部修改会破坏一致性来源。

## 这个 skill 不做什么

- **不替用户选方向**。0.2.5 提供六套表面配方与六套排印配方，但选哪套由 G0 的用户决定（或明确授权自主）。给色板 ≠ 替人定色板。
- **不做组件库**。不生成 Button/Card 的通用实现，只生成这一页需要的。
- **不自动判分**。十问和矩阵是清单，不是脚本。能做脚本的部分（对比度、刻度去重、首屏元素计数）在 craft-floor 和 critique 里给了检测方法，但结论仍由执行者填。G0 也是自然语言契约，**没有 schema 强校验**；模型若伪造一份用户确认，机制本身无法自动识别。**S1.5 同理**：P0 是否真的"反常且不可能被编造"无法机器判定，只能靠第十问的人眼复核。
- **不替代视觉审阅**。它降低"说不清为什么"的比例，不保证结果好看。**它保证的是：每一处取值都有出处，且知道自己放弃了什么。**
