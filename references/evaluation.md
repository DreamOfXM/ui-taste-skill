# 验证 skill 是否真的改善作品

只在维护 skill、比较版本或调查模型差异时阅读，不给每个设计任务增加基准测试负担。文档合规、功能正确、视觉完成度和用户偏好分别验证。

## 固定条件，分开变量

不要用“模型 A 做网页、模型 B 做软件”推导模型能力差异。记录模型具体版本、实际读入的 skill 版本、输入内容、平台与视口、工具/读图能力、项目已有规范、时间或迭代预算。无法确认的记录为未知。

先选择一个用户真正关心的任务，固定功能、数据和状态。用同一模型比较旧/新 skill，再用另一模型重复；或先在同一任务上比较两个模型的当前版，再做版本对照。每个条件独立会话，避免后一份答案看见前一份方案；不要给新版额外素材却把收益全部归因于规则。

自动运行不是前提。没有另一模型接口、额度或目标运行环境时，只做现有可执行的部分，明确其他格未运行，不伪造跨模型验证。

先用一个真实任务做最小对照：模型 A / B 分别使用旧版 / 新版，四个独立会话，输入素材、目标视口、工具和预算保持一致。隐藏来源后让用户选择，也允许打平或都不满意；有改善再换任务或重复运行。单次胜出是线索，不是稳定提升的证明。若新版多了示范素材，报告“规则与资源整体改动”的效果，不把收益全部归因于文字规则。

## 分辨失败发生在哪一层

| 实际证据 | 下一步实验 | 不能直接推断 |
|---|---|---|
| 引用没读、图像没进入模型、界面没运行 | 修正执行链后重跑同题 | 模型审美差 |
| 自由设计差，给明确参考后明显改善 | 优先改参考选择与具体适配支撑 | 模型已掌握所有视觉设计 |
| 参考明确但区域、字体和状态还原失真 | 冻结方向，给可执行规格测试实现 | 原参考不好 |
| 功能与还原成立，但用户仍不喜欢 | 对比不同完整方向，记录具体选择 | 用户要求不合理 |
| 同输入同工具下多个任务都稳定落后 | 再检验模型能力与预算是否是瓶颈 | 只凭 Flash / Max 名称排名 |

本地包中的原创示范是教学材料；即使可运行、截图已复核，也不算按新版规则进行的独立生成实验，更不代表用户认可。

## 专门验证是否提高了美感，而非只减少缺陷

比较旧版与新版时，分别记录“功能和缺陷是否改善”与“作品是否更值得欣赏”。隐藏模型、版本、作者说明和测试成绩，在同内容/视口/状态下比较构图吸引力、排印节奏、材料质量、产品气质与跨页完整性；每项指出画面关系，也允许打平、各有优势或两者都不满意。没有明显错误不能自动赢过有表达力的作品；有漂亮封面也不能抵消内容和能力丢失。

最小四格实验只是起点。要声称跨模型可迁移，至少再覆盖不同屏幕目的和重复运行，记录不成功的产物；用没有出现在内置示范里的产品与内容，避免只是抄出另一份标本库。较强与较弱模型在同样素材/工具条件下比较；如给弱模型额外视觉执行包，应另标为“有设计指导的实现”，不能与无指导自由设计混成一个结果。

若新版只减少视觉缺陷、没有提高整体吸引力，明确记为“提高下限，尚未证明提高审美上限”。没有可用模型接口就记录哪些组合未运行，不用同一模型的多个代理冒充跨模型。任何有限测试都不能证明所有模型、所有任务必然产出极具美感的界面。

## 小规模回归任务

至少保留一个网页任务和一个高密度软件任务，资源允许再扩展。所有数据使用获准的素材或明确标示的示例，不展示真实隐私。

| 任务 | 保持不变 | 重点观察 |
|---|---|---|
| 已认可的网页继续精修 | 同一内容、图像、视口与认可方向 | 能否修细节而不推翻原有气质；不能为了“真实”自动替换好用的示意 |
| 桌面素材/文件工具 | 同一对象与能力：查看集合、检查详情、收藏和设置；不冻结旧页面结构 | 能否基于任务重组差的架构；主次、视觉完成度与操作是否不逊于匹配成熟产品；缩窗与选择是否成立 |
| 中文高密度 Web 工作台 | 长名称、足量记录、状态告警、批量操作 | 不靠删列、巨大留白或隐藏必要操作换干净截图 |
| 移动 App 的对象到详情 | 同一输入、内容、返回及失败状态 | 触达、键盘、安全区和状态连续性，不能只是缩小桌面 |
| 局部改动 | 仅指定控件及相关状态 | 不因新规则强制两稿、换风格、重建架构 |

为每个任务保留原输入与实际产物，截图对应版本和状态；候选顺序随机或隐藏模型/版本名称，避免说明影响偏好。

## 四层证据，不合并成虚构分数

1. **包完整性**：frontmatter、版本、相对链接、离线资产、安装测试。只能证明 skill 可读取、资源可找到。
2. **执行与功能**：确实读了匹配参考、遵循范围；搜索、选择、返回、错误等实际运行。DOM 断言不能证明真实布局。
3. **视觉**：当前版本真实截图，目标视口和内容一致；整体、细节、多页与关键状态分别看。独立评审者先看画面和任务，不读作者自夸说明；模型意见不等于用户意见。
4. **偏好**：用户选哪一个、具体为什么、适用场景。记录未选或打平；不能把作者推荐写成用户认可。

比较时问：是否真正理解任务并有依据地决定保留、重组或重做，而非机械修补或强行推倒？哪里有明确主次与气质？对照匹配成熟产品是否仍有明显完成度差距？是否损失功能或效率？改进是否延续到内页？所有判断都指向画面位置或行为，不用“设计 92 分”代替分析。测试同时包含“坏架构应重构”和“好设计只需局部修正”，避免把变动大误判为能力强。

通过包检查、更新原则或增加参照都不证明设计能力已提升。只有当前版本在相同任务、可比输入下产生更好的实际画面与体验，才构成效果证据；未跑生成实验就明确尚未验证。

## 短记录模板

```text
任务与冻结输入：
模型 / skill版本 / 实际加载证据：
工具、读图与运行能力；预算：
产物入口、版本、视口和状态：
包检查与功能结果：
视觉观察（位置 → 关系 → 后果）：
用户选择及理由（未反馈则写未反馈）：
失败/未运行项；下一步最小实验：
```

若新版只让方向文档更完整，但画面没改善，就没有证据称审美升级成功。若改进只出现在网页，不宣称软件也已证明。若模型未读参考、无法看图或运行失败，先归为执行链缺口，不能直接认定规则无效或模型没有设计能力。
